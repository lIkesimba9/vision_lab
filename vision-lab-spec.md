# ТЗ: библиотека vision-lab

**Версия:** 0.2 (draft) · **Дата:** 2026-07-12
**Область:** классификация изображений + self-supervised предобучение.
Детекция, сегментация, 3D, мультимодальный fusion — вне скоупа v1, но
закладываются архитектурно (см. §3.3).

**Происхождение:** библиотека не пишется с нуля — она **выращивается
извлечением проверенного кода** из существующего SSL/metric-learning
прототипа (дерматоскопия, BYOL/DINOv2 + зоопарк голов). Уроки прототипа
сведены в §12 и вшиты в требования по всему документу.

---

## 1. Цель и назначение

`vision-lab` — переиспользуемая Python-библиотека (pip-пакет) для обучения
моделей компьютерного зрения. Библиотека содержит **только код фреймворка**:
трейнеры, датасеты, сэмплеры, аугментации, лоссы/головы, инференс,
эталонные конфиги-шаблоны.

Конкретные задачи (данные, эксперименты, конфиги, результаты) живут в
**отдельных тонких task-репозиториях**, которые ставят библиотеку как
зависимость с пином версии (`vision-lab==x.y.z`).

### Мотивация разделения

- Экономия контекста при работе с кодовыми агентами: агент в task-репе видит
  10 конфигов конкретной задачи, а не свалку из сотен экспериментов.
- Воспроизводимость: эксперимент = версия библиотеки + версия манифеста данных
  + конфиг.
- Чистая история git и переиспользование пайплайнов между задачами.

### Анти-цели

- НЕ фреймворк-монолит со своим CLI-раннером «на все случаи» (как mmpretrain).
- НЕ обёртка-MCP: знание о библиотеке доставляется агенту через skills и код.
  MCP появляется только если возникнет внешний сервис (трекер экспериментов,
  кластер) — и тогда берётся готовый, а не пишется свой.

## 2. Технологический стек

| Слой | Выбор | Обоснование |
|---|---|---|
| Каркас обучения | **PyTorch Lightning** | Полный контроль над `training_step` (multi-task, ArcFace, EMA-учитель), при этом DDP/AMP/чекпоинты из коробки. HF `Trainer` отвергнут: спроектирован под «модель из хаба + один лосс». |
| Конфигурация | **Hydra** | Композиция групп (`model`/`loss`/`optimizer`/`data`/`trainer`/`transforms`), `_target_`-инстанцирование, кастомные resolver'ы. |
| Бэкбоны | **timm**, при необходимости `transformers` | HF-экосистема — поставщик моделей и компонентов, не каркас. |
| CPU-аугментации | **albumentations** (+ OpenCV-загрузка) | Тяжёлые одно-вьюховые рецепты для классификации, декод/resize для SSL. |
| GPU-аугментации | **kornia** (`AugmentationSequential`) | Батчевые стохастические вьюхи для SSL внутри `forward` — N независимых вьюх одного тензора (см. §6). |
| SSL-модули | **Порт из прототипа** (BYOL, DINOv2/iBOT); lightly — как источник отдельных компонентов при расширении | В прототипе уже есть боевые, сверенные реализации с нужными кастомизациями (positive-shuffle, иерархические лоссы), которых в lightly нет. |
| Бенчмарк-референс SSL | **solo-learn**, авторские репы | Не зависимость — референс чисел для сверки реализаций. |
| Версионирование данных | **DVC** (или объектное хранилище + хеши в манифесте) | Данные вне git; в git task-репы — только манифесты/указатели. |

## 3. Структура пакета

```

├── vision_lab/
│   ├── core/                  # доменно-нейтральный фундамент
│   │   ├── module.py          # базовые LightningModule (cls-трейнер, ssl-трейнер)
│   │   ├── callbacks/         # чекпоинтинг (top-K по нескольким метрикам), логирование
│   │   ├── schedules.py       # EMA-tau, teacher-temp, freeze-расписания
│   │   └── checkpoint.py      # контракт переноса весов (см. §4.4)
│   ├── data/
│   │   ├── manifest.py        # сэмпл-центричный манифест-датасет (см. §7)
│   │   ├── decoders/          # реестр декодеров: png, jpeg, dicom, ...
│   │   ├── samplers/          # PK-семейство + DDP-mixin (см. §5.4)
│   │   ├── transforms/        # albumentations-рецепты (CPU)
│   │   ├── preprocessing/     # color constancy, пер-source выравнивание (§7.4)
│   │   └── taxonomy.py        # иерархия меток
│   ├── models/
│   │   ├── backbones.py       # timm-обёртки: вектор / фичемапа / токены (§4.1)
│   │   └── fusion.py          # (резерв v2: мульти-бэкбон, late/mid fusion)
│   ├── heads/                 # ClassifierHead-семейство: голова владеет
│   │                          # весами классификатора И лоссом (§4.2)
│   ├── losses/                # свободные лоссы (triplet, supcon, ssl-лоссы)
│   ├── ssl/                   # BYOL, DINOv2: самодостаточные nn.Module (§4.3)
│   │   └── gpu_augs.py        # kornia-построители вьюх с инвариантами порядка (§6.3)
│   ├── classification/        # LightningModule'ы: binary, multi-class,
│   │                          # multi-label, multi-task, hierarchical
│   ├── inference/             # единая точка: load_module → transform → TTA (§5.5)
│   ├── eval/                  # kNN-probe, linear-probe (§5.6)
│   ├── experimental/          # НЕ-боевые головы/методы (Proto, Speaker, Sheaf...)
│   └── configs/               # эталонные Hydra-конфиги-шаблоны
├── .claude/skills/            # classification, ssl-pretraining, losses, data, augs
├── CLAUDE.md                  # КОРОТКИЙ: карта пакета, соглашения, команды
├── tests/
└── pyproject.toml
```

### 3.1 Правила границ

- `core/` и `data/` не знают о доменах. Если доменный код требует `if`-веток
  в `core/` — доменная логика уезжает в подпакет домена.
- Правило: «меняется вместе — живёт вместе». Классификация и SSL делят
  бэкбоны, данные, инфраструктуру → живут вместе.
- **Боевое отделено от экспериментального**: непроверенные головы/методы живут
  в `experimental/` и не импортируются боевыми модулями. Перевод в боевые —
  через сверку метрик (урок прототипа: в одном `heads.py` смешались CE и
  Sheaf-ADMM, модуль стал нечитаемым).

### 3.2 Внешние экосистемы задач

Тяжёлые доменные экосистемы подключаются **только как поставщики компонентов**,
никогда как каркасы (второй трейнер/конфиг-система рядом с Lightning+Hydra
запрещены):

- **MONAI** (3D) — сети и трансформы, через extras `[3d]`;
- **segmentation_models_pytorch** — энкодер-декодер архитектуры;
- **ultralytics / mmdetection** — НЕ подключать; детекция либо на компонентах
  torchvision, либо отдельным проектом (первый кандидат на выделение).

### 3.3 Расширяемость (заложено, не реализуется в v1)

Библиотека растёт вдоль двух осей:

- **Ось задач** (что предсказываем): сегментация (маска = плотный таргет,
  инфраструктурный близнец классификации), depth estimation (dense regression),
  детекция (с оговоркой §3.2). Каждая задача = подпакет поверх `core/`+`data/`.
- **Ось данных** (что на входе): 3D-объёмы (новые декодеры, 3D-трансформы,
  patch-sampling — трейнеры не меняются), RGB-D, мультикамерные наборы
  с fusion (несколько бэкбонов — это просто более сложный `nn.Module`;
  подпакет `models/fusion.py` + конфигурируемые стратегии слияния).

Оба направления уже покрыты контрактом данных (§7.2: сэмпл с N входами и
N таргетами) и контрактом бэкбона (§4.1: вектор / фичемапа / токены).

## 4. Контракты компонентов (ядро архитектуры)

Проверенный на прототипе набор интерфейсов — главное, что делает возможным
«один трейнер на любую голову» и чистый перенос весов между стадиями.

### 4.1 Бэкбон

Три формы выхода, выбираются обёрткой, а не форком модели:

- `EmbeddingBackbone` → `{"embeddings": (B, D)}` — пулинг-вектор
  (классификация, metric learning);
- `SpatialBackbone` → фичемапа `(B, C, H', W')` — для голов, которым нужна
  пространственная сетка (в перспективе — сегментация/детекция);
- `TokenBackbone` → `(global_vector, patch_tokens, grid)` — унифицирует
  ViT (CLS+patch), Swin (channels-last) и CNN; нужен DINO/iBOT.

Любая timm-модель по имени из конфига; `num_classes=0` → feature extractor.

### 4.2 Голова (`ClassifierHead`)

Голова **владеет весами классификатора и функцией потерь**:

- `forward(embeddings, targets) → {"total_loss": ..., ...}` (доп. лоссы —
  отдельными ключами для логирования);
- `predict_logits(embeddings)` — инференс без таргетов.

Следствия: один `ClassificationTrainer` обслуживает CE/BCE/AAM/SubCenter/
Focal/LDAM/... без разветвлений; `inference/` единообразен для любого
чекпоинта (`head.predict_logits(model(x)["embeddings"])`); FC-веса
переносимы между стадиями отдельно от бэкбона.

### 4.3 SSL-модуль

Самодостаточный `nn.Module`: владеет бэкбонами (online/target), проекционными
головами **и GPU-аугментациями**; `forward(batch) → dict лоссов`.
Расписания (EMA-tau, teacher-temperature, freeze-last-layer) живут в
Lightning-трейнере (`core/schedules.py`), а не зашиты в модель — модель и
трейнер тестируемы по отдельности.

### 4.4 Чекпоинт-контракт

- Утилита `strip_prefixes` распознаёт и срезает префиксы всех стадий
  (`model.backbone.`, `model.backbone.model.`, `model.teacher.backbone.`) —
  **чекпоинт любой стадии грузится в чистый бэкбон**. Список префиксов —
  единый реестр в `core/checkpoint.py`, покрыт тестами.
- Отдельная утилита переноса FC-весов головы.
- Политика загрузки: `torch.load(weights_only=True)` по умолчанию; небезопасная
  загрузка — только явным флагом для доверенных Lightning-чекпоинтов.

## 5. Функциональные требования

### 5.1 Классификация (`vision_lab/classification`)

- Типы пайплайнов: **бинарная**, **многоклассовая**, **multi-label**,
  **multi-task** (несколько голов, маскирование невалидных меток, взвешивание,
  метрики на голову), **иерархическая** (предки из таксономии, §7).
- Зоопарк голов (порт из прототипа, всё через единый `ClassifierHead`):
  - softmax-семейство: CE, BCE (+class-balanced pos_weight), label smoothing;
  - angular margin: CosineCE, AAM/ArcFace, Sub-center ArcFace;
  - long-tail: Balanced Softmax, Focal (+CB), LDAM, Logit Adjustment,
    Seesaw, VS, DBM;
  - метрические: Triplet (semi-hard), AAM+Triplet, SupCon.
- **Принцип baseline-first** (урок прототипа, §12): эталонный конфиг каждого
  пайплайна — **CE + сильные аугментации**. Зоопарк лоссов доступен, но
  каждый эксперимент сравнивается с этим бейзлайном, а не запускается вместо
  него.

### 5.2 Предобучение (`vision_lab/ssl`)

- Стартовый набор — **порт боевых реализаций прототипа**: **BYOL** (первым —
  он рабочий на реальных данных), **DINOv2-стек** (DINO multi-crop
  self-distillation + iBOT masked modeling + KoLeo + Sinkhorn-Knopp).
- Кастомные приёмы прототипа — как конфигурируемые опции BYOL:
  - **positive-shuffle** (внутриклассовое перемешивание вьюхи-2 →
    supervised-contrastive без негативов), с исключениями
    (`no_shuffle_labels`) и выбором источника группировки: целевой класс /
    самый тонкий доступный уровень иерархии / именованный уровень;
  - **multi-crop** (локальные вьюхи только через online-энкодер);
  - **иерархические SSL-лоссы** (BYOL + labeled-член на уровнях иерархии).
- iBOT block-masking выровнен по выходной сетке токенов (SimMIM-style для
  Swin), с гарантией «не всё и не ничего».
- Выход — чекпоинт бэкбона, загружаемый в `classification/` через §4.4.
- Новые методы при расширении — компоненты lightly / порт авторских реп,
  со сверкой чисел (solo-learn, оригинальные статьи) до включения в боевые.

### 5.3 Semi-supervised

- Размеченные + неразмеченные данные: два подмножества одного манифеста
  (фильтр по null-меткам), два даталоадера, `CombinedLoader`.
  Без фейковых меток и отдельных папок.

### 5.4 Сэмплеры (`vision_lab/data/samplers`)

Структура батча — это часть метода (triplet/SupCon/positive-shuffle не
работают без гарантии позитивов в батче). Порт из прототипа:

- `PKCoverageBatchSampler` — полное покрытие датасета за эпоху (класс режется
  на блоки по K, батч = P блоков разных классов);
- `PositivePairsBatchSampler` — простой PK;
- `PKBatchSampler` — PK с температурным сэмплированием (`counts**alpha`).

Все — через общий **DDP-mixin**: каждый ранг строит один и тот же список
батчей (единый seed на эпоху) и берёт срез `batches[rank::world]` — нет
дублей между GPU и дедлоков. Трейнер выставляет
`use_distributed_sampler=False`.

### 5.5 Инференс (`vision_lab/inference`)

**Единственная точка** инференса (урок прототипа: логика была размазана по
~20 скриптам): `load_module → build transform → predict`, с опциональным
**flip-TTA** (identity/hflip/vflink/rot180, усреднение логитов). Фикс TTA или
нормализации в одном месте чинит всё.

### 5.6 Оценка и отбор чекпоинтов (`vision_lab/eval`)

- Для SSL — **онлайн kNN-probe и linear-probe** (галерея/квери сплит из
  train), отбор чекпоинтов по целевой метрике (напр. macro-F1), а не по
  proxy-лоссу.
- Чекпоинт-коллбек хранит **отдельные top-K по каждой метрике** (kNN, probe,
  их среднее) — пики приходятся на разные эпохи.
- Валидация kNN-метрик — полный набор на каждом ранге (детерминизм в DDP).

## 6. Конвейер аугментаций

Двухуровневая архитектура (проверена прототипом; урок: **рецепт аугментаций
может влиять на качество сильнее выбора лосса и бэкбона** — это полноценный
объект проектирования, а не обвязка).

```
диск ─► CPU (DataLoader worker) ─► GPU (внутри training_step)
        OpenCV + albumentations     kornia.AugmentationSequential
```

### 6.1 Распределение по уровням

- **Классификация**: тяжёлые аугментации на CPU (albumentations), одна вьюха
  на шаг. Библиотека поставляет эталонные рецепты трёх весов:
  light / medium / **heavy** (порт «hugeron»: геометрия + blur/noise +
  дисторсии + цветовые + CLAHE).
- **SSL**: CPU-трансформ минимален (decode → resize → tensor), **вся
  стохастика и Normalize — на GPU через kornia** внутри SSL-модуля. Причина
  жёсткая: нужны N *независимо* аугментированных вьюх одного тензора; CPU-augs
  дали бы всем вьюхам одинаковую аугментацию и убили бы контраст.
- Асимметричные вьюхи для BYOL (разный blur/solarize по вьюхам), DINO
  multi-crop рецепт (2 глобальных + n локальных с разными scale/blur).

### 6.2 Каноничность стеков

Урок прототипа: параллельные «семантически похожие» рецепты в albumentations
и kornia расходятся и невоспроизводимы 1:1. Требование:

- у каждого рецепта — **один канонический стек** (CLS-рецепты: albumentations;
  SSL-вьюхи: kornia); порт между стеками не поддерживается;
- рецепты именуются и версионируются (`heavy_v1`), имя рецепта фиксируется
  в логе эксперимента.

### 6.3 Инварианты — в коде, а не в комментариях YAML

Порядок kornia-аугментаций range-хрупкий (напр., GaussianNoise обязан стоять
последним перед Normalize, иначе device-assert в gamma/CLAHE/grayscale).
Требование: `ssl/gpu_augs.py` предоставляет **builder, который валидирует
порядок** (assert с внятным сообщением) — контракт нельзя нарушить правкой
YAML. Аналогично builder делает `_convert_="all"` для Hydra (ListConfig
ломает interpolate/kornia).

### 6.4 Производительность CPU-уровня

В точке входа обучения принудительно: `cv2.setNumThreads(0)`,
`OMP/MKL/OPENBLAS_NUM_THREADS=1` — OpenCV/BLAS не конкурируют с
DataLoader-воркерами.

## 7. Данные

### 7.1 Принцип

**Пиксели и разметка раздельны, связь — через манифест.** Никаких
`ImageFolder`: структура папок не кодирует ни метки, ни домен.

### 7.2 Манифест: строка = сэмпл (не изображение)

Parquet (типизированные nullable-колонки). Сэмпл имеет **N входов и
N таргетов** — это сразу покрывает мультимодальность, RGB-D, 3D и плотные
таргеты будущих задач; для классификации вырождается в один вход + скалярные
метки.

| колонка | тип | описание |
|---|---|---|
| `sample_id` | str | стабильный идентификатор |
| `input_<modality>_path` | str, nullable | по колонке на модальность (rgb, depth, cam2, volume...); null = модальность отсутствует |
| `raw_<modality>_path` | str | оригинал (source of truth) |
| `source_format_<modality>` | str | dicom / png / jpeg / nifti / ... |
| `source` | str | **домен/источник съёмки** (устройство, клиника) — обязательная колонка, см. §7.4 |
| `label_<task>` | nullable | по колонке на задачу/уровень; null = не размечено |
| `<target>_path` | str, nullable | плотные таргеты файлами (mask, depth_gt...) — резерв |
| `split` | str | train / val / test |
| `conv_params` | struct | параметры конвертации (DICOM: window и т.д.) |

- **Иерархия**: в манифесте — самая специфичная метка; таксономия — отдельный
  версионируемый `taxonomy.yaml`; предки выводятся кодом. Цепочка предков НЕ
  денормализуется в манифест.
- **Версионирование**: манифесты иммутабельны — дозразметка = новый
  `manifests/v{N+1}/`; старые эксперименты ссылаются на свою версию.

### 7.3 Форматы и DICOM

- Реестр декодеров по `source_format_*`; датасет один на все форматы.
- DICOM не декодируется на лету. **Офлайн-этап**: DICOM → 16-bit PNG/npy,
  параметры (window center/width, MONOCHROME1-инверсия, rescale
  slope/intercept) фиксируются в `conv_params`. Оригиналы immutable.

### 7.4 Доменная предобработка (`data/preprocessing`)

Порт из прототипа, обобщённый:

- **Color constancy** (Shades-of-Gray) — детерминированная инвариантность к
  освещению/устройству, одинаково на train и inference. (Нюанс реализации:
  приведение обратно к float32 после numpy-промоушена.)
- **Пер-source выравнивание**: для каждого источника заранее считаются
  mean/std (скрипт в библиотеке), при загрузке изображение линейно
  переносится в глобальный референс — междевайсный сдвиг убирается,
  внутридевайсный цвет сохраняется.
- **Требование (фикс техдолга прототипа):** источник берётся **только из
  колонки `source` манифеста**, никогда из парсинга пути. Отсутствие
  статистик для source — **ошибка, а не тихий фолбэк** на глобальный референс.
- **Требование:** загрузка/парсинг файлов статистик — одна реализация в
  библиотеке; eval-скрипты переиспользуют её, не копируют.

## 11. Нефункциональные требования

### 11.1 DDP-корректность (проверено прототипом)

- Кастомные сэмплеры сами шардят по рангам (§5.4),
  `use_distributed_sampler=False`;
- kNN-валидация — полный набор на каждом ранге (детерминизм);
- `bf16-mixed` (без grad-scaler), `sync_batchnorm=True`;
- один seed на эпоху для построения батчей на всех рангах.

### 11.2 Соглашения кода

- Код и идентификаторы — английский; доки и комментарии — один язык на весь
  репозиторий (выбрать и зафиксировать в CLAUDE.md).
- Запрещён бесформенный `squeeze()` (роняет batch-размерность при B=1) —
  только `squeeze(dim)`.
- Неявные контракты (порядок аугментаций, диапазоны значений) кодируются
  assert'ами в builder'ах, а не комментариями в YAML (§6.3).
- `torch.load(weights_only=True)` по умолчанию (§4.4).

### 11.3 Прочее

- Python-пакет с semver; тяжёлые зависимости — в extras
  (`[dicom]`, `[3d]`, ...).
- Тесты: unit на головы/лоссы/таксономию/декодеры/чекпоинт-префиксы/сэмплеры
  (включая DDP-шардинг); smoke «1 батч через каждый тип пайплайна» на
  синтетике; сверка SSL с референсными числами.
- Single-GPU и DDP без изменения кода задачи.

## 12. Уроки прототипа (зафиксированные выводы)

Эмпирика, определившая приоритеты этого ТЗ:

1. **Простой CE обыграл весь long-tail зоопарк** (Focal/LDAM/Seesaw/VS/...).
   → Принцип baseline-first (§5.1): зоопарк доступен, но бейзлайн священен.
2. **Тяжёлый рецепт аугментаций — главный драйвер качества** (~0.10 F1 в
   бинарном треке) — больше, чем выбор лосса и бэкбона.
   → Аугментации — полноценный объект проектирования (§6), рецепты
   именуются и версионируются.
3. **BYOL оказался рабочим SSL-методом, DINO/iBOT — нет** (на тех данных).
   → BYOL портируется первым; методы добавляются по потребности, а не
   «для полноты».
4. **Отбор SSL-чекпоинтов по kNN/probe-метрике, не по лоссу**; пики разных
   метрик — на разных эпохах → top-K на метрику (§5.6).
5. **Единые контракты (backbone-dict / head / SSL-module) окупились**:
   один трейнер на любую голову, единый инференс, перенос весов между
   стадиями (§4).
6. Техдолг, превращённый в требования: опечатки в именах API (§8),
   домен-из-пути (§7.4), дублирование парсинга статистик (§7.4),
   два несогласованных стека аугментаций (§6.2), range-хрупкий порядок
   augs (§6.3), `weights_only=False` (§4.4), experimental вперемешку с
   боевым (§3.1), бесформенный `squeeze()` (§11.2).

## 13. Этапы разработки

Стратегия — **извлечение из прототипа**, не переписывание с нуля:

1. **Каркас**: `core/` (базовые модули, расписания, чекпоинт-контракт §4.4),
   Hydra-скелет + resolver'ы, CI (включая spell-check имён), тесты.
2. **Данные**: сэмпл-центричный манифест (§7.2), реестр декодеров (png/jpeg),
   taxonomy, DICOM-конвертация; порт preprocessing (color constancy,
   пер-source выравнивание — с фиксами §7.4) и PK-сэмплеров с DDP-mixin.
3. **Аугментации**: albumentations-рецепты (light/medium/heavy_v1) +
   kornia-builder'ы с инвариантами (§6.3).
4. **Классификация**: контракт `ClassifierHead` + порт голов (CE первым,
   затем angular-margin и long-tail семейство); multi-task, hierarchical.
5. **SSL**: порт BYOL (с positive-shuffle, multi-crop, иерархическими
   опциями) → kNN/linear-probe eval и top-K чекпоинтинг → порт DINOv2-стека.
   Сверка чисел с прототипом на его данных (регрессионный тест миграции).
6. **Инференс**: единый модуль с TTA (§5.5).
7. **Semi-supervised**: CombinedLoader-пайплайн.
8. **Обвязка**: эталонные конфиги, skills, шаблон task-репы (cookiecutter);
   `experimental/` — перенос Proto/Speaker/Sheaf-голов как есть.
9. **Миграция**: живые эксперименты прототипа — в task-репы, мёртвые — в
   архив; прототип замораживается как референс для регрессионных сверок.
